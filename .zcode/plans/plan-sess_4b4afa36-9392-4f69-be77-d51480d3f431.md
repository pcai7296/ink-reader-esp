# 静态内存裁减 + 自由堆提升计划

## 现状（build/ink-reader-esp.ino.map 实测）

- RAM 已用 **69368B / 80192B (86%)**：DATA 1712 + **RAM 常驻 RODATA 18144** + BSS 49512
- 自由池 = 80192 − 69368 ≈ **10.8KB**（扣 4KB 系统栈后，配网会话实测仅 ~3-5KB，是 esf_buf 崩溃的土壤）
- 大头构成：fb 帧缓冲 4736（不可动）、**chapterPageOffsets 4096**、Web/HTTP 静态 scratch 约 **4.6KB**、RAM 字符串常量 **~6-7KB（用户代码部分）**、gBooks 864、winItems 864、gFpBuf+gBuf 1280、diagRing 256（只写不读的死数据）

## 分批方案（P0→P5，每批独立可验证、可单独回退）

### P0 删除死数据（~580B，零风险）
1. `diagRing`(256B) + `diagRingHead`：全仓只写不读（ino:91,139-150），直接删写入与定义（trace 文件/串口路径不受影响）
2. `chapterRowOffsets`(24B, ino:743)：唯一写点 :4724，零读者
3. `gOfsUpPhasePath`(300B, file_api_fs.cpp:478) + getter `ofsUpGetPhasePath()`(.h:29)：全仓零调用者（同 gOfsDlPhasePath 已删先例）；保留 `ofsUpGetPhase()`

### P1 章节目录懒分配（~4.5KB）
- `chapterPageOffsets`(4096B) + `chapterRows`(408B) 合并为**一块 malloc**（4504B）：
  - 分配点：`enterChapterList()`(:4967，本来就每次重建表) + 睡眠唤醒恢复分支(:5990)
  - 释放点：`closeTxtReader()`、章节跳回 APP_READER(:6687)
  - 失败降级：malloc 失败 → `chapterPageTableCount=0`，`chapterPrevPage`(:4848) 已有 `seekChapterOffset` 全扫兜底，功能不丢
- 全局指针替换数组引用（引用点：4741-4855、4913-4917、6002-6005、6678 等约 8 处）

### P2 Web scratch 共享池（BSS ~4.6KB → 池 ~1.5KB，净省 ~3KB）
- 七组 static 缓冲已证实**跨请求两两互斥**（单线程 handleClient，handler 不可重入）：
  `/fs/list`(gLsPath300+buf640+nameEsc512)、PUT edit(gOpPath/A/B/C/Lab=1420)、DELETE edit(gOpPath+Lab+C)、GET file(path300)、上传(ofsUpPath300)、`/fm`(buf512)、`gApiParent`(300)
- 实现：一个 `gWebScratch[1456]` 文件级池 + 每组定长槽位映射（union 语义，不做运行时分配，不改栈局部——HTTP 深链栈 0-100B 是铁律）
- 注意：上传 ofsUpPath 跨 START→DONE 多回调，占槽期间无并发请求（单线程天然保证）

### P3 进度同步缓冲懒分配（~1.28KB）
- `gFpBuf`(1024B)：只在 `computeFileFingerprint()`(progress_sync.cpp:375-396) 内活 → 改函数内 malloc/free，网络阶段前归还
- `gBuf`(256B)：`progressSyncBegin` 时 malloc，`progressSyncDone/Cancel` free
- `gFpH0/1/2`(123B) 与状态机变量保持常驻（很小）

### P4 统计会话级加载（864B，按推荐：改）
- `gBooks` → `statsOnSessionStart` 时从 LittleFS books.dat 载入 malloc，`statsOnSessionEnd`/`statsTick` 写盘后 free；`renderStatsPage` 无会话时懒加载
- 分配失败（极端低堆）→ 该次翻页不计入统计 + trace 日志；正常路径零行为变化

### P5 RODATA 字符串扫荡（RAM 省 3-4KB，flash +4KB 左右）
- ESP8266 的裸字符串字面量落在 DRAM；map 显示 sketch+自有模块的大项：ino(3ae+26e+22b+13e+119+117+100)、file_api(1e4+aa+61)、file_api_fs(2ee+72)、wifi_manager(240+12a)、weather_data(192) 等
- 机械扫描以上文件中 `snprintf/Serial.printf/traceFmt` 的裸字面量 → `PSTR()`/`F()`（本项目 traceFmt/PSTR 基建现成）
- 只转字面量，不碰 vtable/typeinfo；flash 90%（余 98KB）足够承接

## 预期收益

| 指标 | 现状 | P0-P4 后 | +P5 后 |
|---|---|---|---|
| BSS 静态 | 49512 | ~39400 | ~39400 |
| RAM 总占用 | 69368 (86%) | ~59600 (74%) | **~56000 (70%)** |
| 自由池 | ~10.8KB | ~20.6KB | **~24KB** |

章节目录、进度同步、Web 管理、统计全部功能保留；阅读模式（续航关键态）堆余量最先受益。

## 验证方案

1. 每批编译对比 DATA/RODATA/BSS 数字（期望逐批下降）+ map 符号核对（diagRing/gOfsUpPhasePath 等消失）
2. 实机 `python esp_dev.py --steps monitor` 回归：
   - 章节目录：进入→翻页→上一页→跳章→退出→重进（含低堆场景），睡眠唤醒直入目录分支
   - Web 管理全端点：list/edit PUT/DELETE/upload/download/fm/status（P2 重点）
   - 进度同步一次完整会话（指纹 PREPARE→GET→COMPARE，P3 重点）
   - 统计页显示 + 翻页计数 + 会话结束落盘（P4 重点）
   - 串口确认 `SD_REINIT`/`PAGE_REC_*` 无异常、boot heap 数字对比
3. 已有 auditHeap 探针在 upload/download 点自动留痕

## 不动清单（评估后放弃）

- `fb` 4736：双缓冲核心，不可动
- `winItems` 864：浏览主 UI 窗口，常驻合理
- `server` 对象(272B)：懒 new 收益太小，不值得动
- `wvfState`(512, core 波形)/`dns_table`(432, lwip)：core/SDK 资产，不动

## 实施顺序与依赖

P0 → P1 → P3 → P4（小而独立，先吃安全收益）→ P2（触及面最广）→ P5（机械扫荡放最后，避免与 P2 改动冲突）。每批一个 git commit，出问题可按批回退。
