# 配网会话堆预算审计报告（2026-08-28, 探针版固件实测）

> 审计目的: 量化配网会话从进入到手机关联/请求各阶段的 heap 水位与峰值需求,
> 决定哪些功能能进入该会话。探针 = auditHeap() 轻量打印（PSTR, 不占堆）。
> 设备: ESP-12F 阅读器, 静态 RAM 69788/80192 (87%), IRAM ~93%。

## 1. 水位曲线（实测串口, 单位字节）

| 阶段 | heap | maxblk | 阶段消耗 | 备注 |
|---|---|---|---|---|
| 阅读空闲（点击配网前） | 8592 | 8408 | 0 | config_enter 探针 |
| AP 创建后（softAP 完成） | 6632 | 6552 | **-1960** | AP 结构（beacon/DHCP/phy） |
| 配网入口完成（路由+LFS+二次mode） | 4824 | 4616 | -3768 | 路由注册 + LFS + 二次 mode |
| AP 空闲稳定（22.5s 采样） | **5192** | — | -3400 | ⚠️ **空闲不塌陷**（推翻此前假设；二次 mode 提前生效） |
| **手机关联瞬间** | **1168** | — | **-7424** | **瞬时 -4KB 峰值（预算黑洞）** |
| 手机关联后稳定（AP_STA_NUM=1） | ~3300 | ~3100 | -5292 | 关联站资源常驻 -1.9KB |
| /api/status 请求入口 | 2728 | **2072** | -5864 | **maxblk 仅 2KB** |
| **请求处理需求** | — | **>2072** | — | **OOM 崩溃（Unhandled C++ exception: OOM 实测）** |

## 2. 关键发现

1. **手机关联瞬间的 -4KB 瞬时峰值是预算黑洞。** 5192 → 1168（关联/DHCP 处理），
   之后虽恢复，但**稳定水位从 5192 掉到 ~3300**（关联站资源常驻 -1.9KB）。
2. **请求处理需要 >2KB 连续块，而关联后 maxblk 仅 ~2072** → 任何需堆分配的
   /api 请求（status/files/search/upload/download）在手机连接后**必 OOM**。
3. **AP 空闲不塌陷**（5192 稳定 22.5s）——之前观测到的 2192 塌陷是
   "二次 mode 在 server.begin 后"（AP 在低堆下重建）造成的；本轮已提前，
   塌陷消失。但手机关联的峰值需求仍在。
4. 安全余量: 3300（关联后）− 请求需求 ~2500 ≈ **<1KB** → 🔴 红色档。

## 4. 决策框架（按用户定义三档）

**🔴 当前 <3KB 安全余量（实测 ~1KB）→ 功能分级, 优先降静态 RAM。**

候选降静态（按用户优先级）:
- idxBuf[2048]（ink-reader-esp.ino 索引构建缓冲）: 仅构建期用 → malloc 化 省 2KB
- recScanBuf（启动扫描缓冲）: 仅启动用 → 复用/动态 省 ~0.5-1KB
- 其他大静态: fb[4608]（帧缓冲, 核心不可动）/ chapterRows / diagRing

若 idxBuf + recScanBuf 释放 ~2.5-3KB: 静态 87% → ~84%, 启动 heap ~11KB,
配网入口 ~6.5KB, 关联后 ~4.5KB → 🟡 3-6KB 档（完整 API + 限制搜索）。
